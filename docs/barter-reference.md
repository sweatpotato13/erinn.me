# Barter preparation data and calculations

`/tools/barter` consumes committed local files. Fixed goods come from the common
Prilus snapshot, which already includes `BarterList`, `CommercePostNameMap`,
`ItemList` and `StringTable`. Raw records, IDs and their checksums are preserved.
The fixed coverage is currently 28 goods: eight at Skatha and five at each of
Karu/Oasis/Calida/Pera. Empty entries from the 17-name post map are not catalogs.
`BarterList.Id` identifies a trade good; only `Prices[].Id` joins to an item.

`scripts/build-barter-reference.ts` uses `readSnapshot` and `resolveItems` to
generate `src/data/barter-reference.json`. The page receives only selected
material metadata. The full, minimal ID/name/searchability index is imported
only by `/api/barter/materials`: name search returns at most 20 results, or an
explicit ID lookup accepts at most 100 IDs. It does not query an external source.
Duplicate names retain separate IDs and cannot automatically share market prices.

## Independently refreshed seasonal supplement

Source: [Labanyu trade calculator](https://labanyu.com/trade). This is an internal
upstream endpoint, not a guaranteed public API. The local Node collector uses
native `fetch`: obtain the visitor cookie and page CSRF in memory, select the
unique season containing the current instant from `__NEXT_DATA__`, then POST
JSON text to `/api/trade/season-item`. Both HTTP success and JSON `code: 200`
are required. HTTP 200/code 500 is a failure. Each request has a 15-second timeout;
unexpected redirects are rejected. No login, API key or additional browser
automation is needed for this collector. Prilus's existing collector remains
independent and retains its own Playwright prerequisites.

The actual upstream field is `tear`. Only tier six at Karu/Oasis/Calida/Pera is
extracted; Skatha tier six is not a monthly rotating entry. `weekCount` is the
exchange limit and ingredient counts are per exchange; `bundleCount` is not
multiplied into those requirements. Upstream item keys are never decoded as game
IDs. Exact ingredient names must match exactly one resolved Prilus ID. Missing
or ambiguous matches fail publication; review the source before introducing any
small, explicitly documented ID mapping. No mapping is currently needed.

The supplement `src/data/barter-season.json` contains only attribution, collection
time, source versions, effective dates and four validated goods with game material
IDs. All four posts must succeed together. A temporary file on the same filesystem
is renamed only after validation; failures retain the previous file. Cookie/CSRF,
unrelated production data and source market observations are never published.

## Maintainer refresh and review

After the first-Thursday monthly rotation, when upstream current data is available:

```sh
# Only if the underlying Prilus references also need refreshing:
pnpm data:collect
# Regenerate the existing consumers affected by any common snapshot refresh.

# Independently collect the current seasonal supplement:
pnpm barter:refresh
# This runs barter:season:collect, barter:build and barter:icons:collect.
pnpm data:check
pnpm exec jest --runInBand src/lib/__tests__/barter.test.ts src/lib/__tests__/barter-state.test.ts
pnpm typecheck
pnpm build
git diff -- src/data/barter-season.json src/data/barter-reference.json src/data/barter-material-index.json
```

Review post coverage, names/IDs, limits, dates, attribution and absence of secrets.
Commit the reviewed supplement and derived files together. A common Prilus refresh
also needs its manifest/raw tables and all affected existing consumer indexes
reviewed together. No collector runs from `prebuild`, deployment, CI, page load or
the materials API. `prebuild` runs the offline builder only; `data:check` runs
deterministic collector fixtures and compares generated bytes.

On a failure, inspect the reported field or network status and fix/retry without
changing the old file's date. To roll back, restore the reviewed supplement and
derived files from the same known-good commit, regenerate and check before
committing the rollback. Do not change raw Prilus barter rows to fill season gaps.
Expired files remain valid historical build inputs; the UI disables expired goods
until the maintained supplement is refreshed. Unknown future rotations are never inferred.

## Input and inventory semantics

- `q` means additional exchanges, and `used` means already exchanged this week.
  Both are nonnegative integers with `q <= limit-used`; invalid values remain
  visible instead of being clamped. Safe-integer bounds apply to products/sums.
- Aggregate chosen ingredients by actual ID first, then allocate owned stock
  once: `usedOwned=min(required,owned)`, `missing=max(0,required-owned)`.
  Duplicate names never merge variants. Choose one alternative per group.
- Checklist changes and recalculation do not consume inventory. Explicit exchange
  recording adds q to used and clears q; undo restores these counts. Users adjust
  inventory themselves. Clearing a plan preserves stock, prices and used counts.
- Weekly rollover is Thursday 07:00 Seoul time, irrespective of device timezone.
  The visible carry-forward action resets only usage. Monthly effective periods
  invalidate seasonal entries separately. Open pages recheck at the next boundary
  and on focus/visibility return; there is no background service.
- Existing shared/saved manual seasons remain readable with verified material IDs
  and explicit source selection. The creation/editing form was removed at user
  request; new plans use maintained seasonal data.
- Replacement value uses required units; additional purchase cost uses deficits.
  Unknown price differs from explicit zero. Price lookup is explicit, deduplicated,
  limited to three concurrent requests, and calls existing validated
  `fetchItemPriceSummary`. Manual overrides, even an explicit blank, take priority.
  No market request occurs while typing or checking rows. Empty observations are
  unknown; partial results and observed stock shortages remain visible. Minimum
  price times deficit is an estimate, not an executable basket or bundle optimizer.

## Local storage, shares and crafting boundary

`erinn-barter-v1` stores versioned drafts, definitions, week key, choices, stock,
prices, observations and checklist state. Restoration finishes before editing;
corrupt or incompatible saved content is retained for inspection. Shared URLs open
temporary plans and never overwrite storage until an explicit import. Source
definitions are compared against the local catalog, not trusted because a URL
claims the current revision. Removed IDs remain visible for review.

Shares are limited to 8,192 encoded query characters and 16,384 decoded UTF-8
bytes; local storage to 256KiB. A plan has at most 100 rows, each with at most
20 groups of 20 alternatives, and maps have at most 1,000 item keys. Oversized
shares offer text export instead of truncation. Text includes counts, deficits,
coverage, period, prices and assumptions. Clipboard failure leaves selectable text.

Issue #196 owns the future live crafting link. `barterDeficits` produces validated
`{itemId,count}` targets **after** barter inventory allocation. The receiver must
mark these as net barter deficits and must not reapply the original local stock.
No inventory is transferred by default; if required later, transfer only
`owned-usedOwned`. Keep the crafting link hidden until `/tools/crafting` ships.
This feature does not perform recursive production, route or profit optimization.

## Verification

`check-barter-season.ts` checks anonymous request shape, dynamic season selection,
HTTP/internal failures, malformed data, missing/duplicate posts, quantities,
name/ID ambiguity, expiry, secret exclusion and write/rename rollback. Unit and
component tests cover the documented 12/6 → 7/4 material example, 2,400/1,500 Gold,
cross-post allocation, alternatives, bounds, independent periods, sharing, storage,
explicit market concurrency/cancellation and legacy manual data. `e2e/barter.spec.ts`
exercises browser preparation, weekly selection, export/import, rollover, metadata
and navigation; existing home and auction calculator regressions remain active.

## Planner presentation

Goods are selected at their remaining weekly limit by default. The limit is a
read-only label; partial plans use a compact quantity control. Prior exchanges
are optional adjustments under **이미 교환했다면**. Four monthly sixth-tier goods
appear together above the fixed post selector. Material rows show required, owned
and missing counts; price and contribution details are secondary disclosures.
See [UI research and decisions](barter-ui-research.md) for the sources reviewed.

`barter:icons:collect` saves the 65 currently referenced material PNGs under
`public/images/barter`. These are local assets at runtime, with a neutral fallback
for custom materials. Refreshing icons is a separate maintainer command and is
never part of prebuild or page rendering.

The visible data-explanation section and manual season entry form were removed
at user request. Attribution, refresh procedures and calculation details remain
in this maintainer document. The page uses the shared MabinogiClassic font and
DaisyUI theme/button tokens, matching the existing calculator.
